\# Day 16 – Security Design Note



\## 1. Project Overview



The Day 16 Knowledge Assistant extends the existing FastAPI Knowledge Assistant with user authentication, session management, access control, and security auditing.



Users must register and log in before accessing the policy assistant.



\## 2. Password Security



\- Passwords are hashed using Argon2id through `pwdlib`.

\- Plain-text passwords are never stored in the database.

\- Passwords must contain at least 15 characters.

\- Passwords of 64 characters or more are accepted.

\- Passwords are checked against a local common-password blocklist.

\- No mandatory uppercase, lowercase, number, or special-character composition rules are applied.

\- No periodic password rotation is enforced.



The current blocklist contains a small set of common passwords. It is a demonstration blocklist, not a comprehensive database of compromised passwords.



\## 3. Session Management



\- Sessions use cryptographically secure random tokens.

\- Only SHA-256 hashes of session tokens are stored in SQLite.

\- Session lifetime is eight hours.

\- Expired and revoked sessions are rejected.

\- Logout revokes the session in the database, not merely in the browser.



Session cookies use:

\- HttpOnly

\- SameSite=Lax

\- Secure when HTTPS deployment is configured.



For local HTTP development, Secure is disabled. It must be enabled for HTTPS deployment.



\## 4. CSRF Protection



The application uses signed double-submit CSRF tokens.



\- A random token is generated by the server.

\- The token is signed using the session secret.

\- The signed value is stored in an HttpOnly cookie.

\- The corresponding token is included in the HTML form.

\- Submitted tokens are checked against the cookie and their signature.



Invalid or missing CSRF tokens are rejected.



\## 5. Login Throttling



\- Failed login attempts are tracked using a hashed email identifier.

\- Five failed attempts within a 15-minute window block further login attempts.

\- Successful authentication clears previous failed attempts.

\- Login failures are recorded in the audit log.



The current implementation uses per-email throttling. Production deployment should also consider IP-based or combined throttling.



\## 6. Access Control



The application uses centralised role-based access control.



Supported roles:

\- employee

\- admin



The admin endpoint requires the admin role. Unauthenticated users are rejected, and employees receive an access-denied response.



\## 7. Object-Level Ownership



Records are associated with their owning user.



The record query checks both the record ID and the authenticated user's ID.



Users cannot retrieve another user's private record. An inaccessible record returns 404, without revealing whether another user's record exists.



The current implementation applies ownership checks to admins as well; admin role alone does not bypass record ownership.



\## 8. Audit Logging



The application records security events, including:



\- USER\_REGISTERED

\- LOGIN\_SUCCESS

\- LOGIN\_FAILURE

\- LOGOUT

\- ACCESS\_DENIED

\- IDOR\_ATTEMPT



Audit entries may include event details and user IDs. Passwords, password hashes, and raw session tokens must not be logged.
